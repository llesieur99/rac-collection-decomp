## Where the project stands

executables of the release are read, their PPU ELF is rebuilt, and the hashes
are pinned. Nothing of the *program* is known yet: no boundary, no name, no
compiled body.

## What is measured

* The release is `BCUS98282`, version `02.00`, application version `01.00`,
  for a system of version `04.2100` or later.
* The volume is `PS3VOLUME`; its descriptor is 1,536 bytes and names the
  title `BCUS-98282`.
* The four executables are SELF containers, version 2, key revision `0x001C`,
  with a local licence and a `0x980`-byte header block.
* Their PPU ELF is ELF64 big-endian, `EM_PPC`, 8 program headers, 35 section
  headers, no symbol table, no conventional section name.
* The text segment of each program starts at file offset `0x0`.
* **The disc holds the game data encrypted and the working copy holds it in
  the clear**: 13,138 files have the same size and a different content, and
  ten metadata files are identical on both sides. The relation is proved in
  [DISC-PROVENANCE.md](DISC-PROVENANCE.md).
* **The code and the data of the executables are still NPDRM-encrypted**:
  7.99 bits per byte for the text, 8.00 for the data, 1.61 for the section
  table, which stays readable. See [COMPILER.md](COMPILER.md).
* **The encryption can be removed**, and it was: `tools/self_decrypt.py`
  rebuilds the PPU ELF in the clear, with the constants of the revision of
  the container. The validation against the sibling project reproduces its
  published analysis exactly — the same 106 stamps, the same libraries, the
  same size. See [NPDRM.md](NPDRM.md).
* **The compiler is named**: `GCC: (GNU) 4.1.1 (SDK400, $Rev: 3538 $)` for
  124 objects and `GCC: (GNU) 4.1.1 (SDK360, $Rev: 3455 $)` for 5, the same
  for the four programs of the release. The sibling's target was built with
  the SDK 270: the two trees are not interchangeable.
* **The names of the sections are lost**: the string table of the ELF is not
  covered by any encrypted section, so it stays encrypted in the container.
  The names of the modules are in the clear, and they are what the project
  uses.
* **The boundaries of the functions are known**: four independent signals —
  the prologue of the SDK, the targets of the calls, the entries of the
  control flow and the returns of the walk — agree, two by two, on 51,463
  functions, of which 47,215 end on a return that no path falls through
  from; 2,315 addresses are still candidates. The names are not known yet.
  See [CATALOGUE.md](CATALOGUE.md).
* **The builds correspond to each other, function by function.** The
  collection's copy of a game and the standalone PlayStation Network title
  of the same game hold the same number of functions, and 99 % of them are
  matched by the body — every matched pair having exactly the same size. The
  engine's own code is shared by the three games, and more than half of
  those pairs are literally the same bytes. See
  [CORRESPONDENCE.md](CORRESPONDENCE.md).
* **The toolchain is built and provisionally qualified**: two builds of the
  Cell OS Lv-2 toolchain — the SDK 2.7.0 and the SDK 4.2.0 — reproduce the
  same six bodies of the launcher byte for byte, and four functions of the
  SDK's runtime are byte-identical in the retail executable. The game was
  built with `-mno-nop-after-bl` on some files and without it on others, and
  that is visible in the code. See [TOOLCHAIN.md](TOOLCHAIN.md).
* The disc carries the digital manual of the collection as a retail package,
  `NPUO70220`. It is not an update of the game.
* The three titles also exist as separate PlayStation Network titles, with
  their own content ids and their own builds:
  [RELATED-TITLES.md](RELATED-TITLES.md).
* **The rebuild is validated against an independent reference.** The container
  of A Crack in Time on this machine is byte for byte the file the sibling
  project `rac8-act-decomp` publishes (`e69f2b5a…`), and the rebuild gives
  exactly the size it publishes, 14,515,416 bytes, with the same entry point,
  the same eight program headers and the same thirty sections. The bytes
  differ only in the encrypted payload: the sibling's hash is the hash of a
  rebuild from a *decrypted* container. See
  [SELF-FORMAT.md](SELF-FORMAT.md).
* **The ELF string table is encrypted too.** The section names are not
  readable while the NPDRM layer is there; the SCE module names, which lie
  just before the section header table, are. See
  [PPU-EXECUTABLE.md](PPU-EXECUTABLE.md).

## What is assumed, and what is not known

* **The content id is derived, not measured.** It is encrypted in the NPDRM
  metadata. `config/target.json` says so.
* **The engine is shared, and it is now measured.** The three titles come from
  one engine: 1,226 functions of `rc1` have a counterpart in the three other
  builds at once, and more than half of those pairs are the same bytes. What
  is not measured is the *name* of any of them — that is the naming, and it
  is not started.
* **The disc's update file has not been read.** `PS3UPDAT.PUP` is on the disc
  and not in the working copy. It may carry a newer launcher.

## What to do next

In order:

1. **Name the functions.** The compiler is known, the toolchain is
   provisionally qualified, the boundaries are known, and the builds
   correspond to each other function by function. What is missing is the
   vocabulary: the strings the code touches, and the sibling projects' names.
2. **Hold the toolchain profile on bodies of other shapes** — with arguments,
   with branches, with arithmetic — so that the profile is not qualified on
   six bodies of the same shape.
3. **Read the update container** of the disc, and decide whether it carries a
   newer launcher than the pinned one.
